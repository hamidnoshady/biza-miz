# ESH-154 existing-business preflight

Run this assessor on an isolated restore or sanitized development copy, never on a production endpoint or a tunnel to one. The assessor issues no changes and does not activate routing. Run it again whenever the tenant data or verified evidence changes.

1. Create an encrypted backup under the existing backup process. Restore it into a separate local database named `esh154_preflight_<label>`. Verify the restore and retain the verification record. Do not point the tool at a database that serves requests.
2. Use a dedicated login with `CONNECT`, `USAGE` on `public`, and `SELECT` on the tables listed below. The login must not own the tables, be a superuser, have `BYPASSRLS`, or have write or role escalation privileges. Do not reuse application or platform-admin credentials. Configure `ESH154_PREFLIGHT_DATABASE_URL` with its local connection URL through your normal secret mechanism.
3. Run `npx tsx scripts/financial-migration-preflight.ts <tenant-uuid>` and retain the JSON in the restricted migration record. Use the report to review actual banks and terminals, approve or retain legacy exceptions, verify posted and unsettled amounts, and check releases and queues on every enrolled client and any disconnected installation. No bank or terminal is assigned from a method label, ledger code, or client device.
4. Run again against the same snapshot with `npx tsx scripts/financial-migration-preflight.ts <tenant-uuid> evidence.json`. Compare against a freshly collected snapshot before relying on a gate. Exit code `0` means `READY`; `2` means a report was produced with outstanding work; `1` means no valid report was produced. A `READY` report is evidence for review, not authority to cut over.

Reader tables: `businesses`, `locations`, `accounts`, `financial_accounts`, `financial_transfers`, `journal_entries`, `journal_lines`, `orders`, `payments`, `payment_methods`, `ar_receipts`, `ap_payments`, `expenses`, `customer_returns`, `bank_reconciliations`, `sync_events`, `site_devices`, `site_device_runtime_status`. Restore a copy with the existing financial accounts and site runtime migrations applied. Historical `payments` can predate the canonical financial source column; the assessor counts those rows as unattributed.

The evidence file contains `tenantId` and the following lowercase SHA-256 digests. They identify separate records already reviewed by the operator. A digest alone does not prove that a backup, restore, terminal allocation or client review happened.

| Field | Reviewed record |
| --- | --- |
| `snapshotSha256` | Fingerprint from the first report. It binds the evidence to the reported snapshot. |
| `encryptedBackupEvidenceSha256` | Encrypted backup verification, with covered tenant and backup identifier. |
| `testedRestoreEvidenceSha256` | Successful isolated restore from that backup, with verification results. |
| `clientAndQueueEvidenceSha256` | Compatible versions and drained queues for all active and disconnected sites, or review confirming none exist. Server telemetry does not prove that a disconnected local queue is empty. |
| `ownerMappingEvidenceSha256` | Owner-approved account/terminal mappings, posting authority and treatment of ambiguous historic records. Retain unattributed history in the pooled ledger where evidence cannot identify a specific account. |
| `pendingSettlementEvidenceSha256` | Verified PSP statements or batch records supporting nonzero balances on registered PSP clearing GLs. Optional only when all those balances are zero. |

The report groups counts by branch ID (`null` means business-wide) and includes the underlying GL and currency totals in integer minor units. It counts distinct active leaf asset GLs linked to the financial registry. The `1110` and `1120` totals are the legacy shared bank and clearing ledgers. Registered PSP balances are posted clearing balances; they are an estimate of unsettled takings and do not assert which batches a provider still owes. Negative tender rows without a source are visible in payment counts. The backlog lists customer returns and reversed AR/AP documents missing their expected journals; provider-side pending operations require the separate reconciliation review. Open bank reconciliations have GL scope, so branch is intentionally not inferred.

Before fingerprints cover the selected accounting fields on source documents and journal rows, in stable order. Reports omit business and person names, memo/reference text, bank identifiers and device identifiers. Share reports only with authorized reviewers: opaque IDs, totals and the version inventory are operational data. Preserve the report so that subsequent phased migration checks can compare it with a snapshot under the same report version.

## Hybrid and Full Offline rollout gate

This release enables explicit order routing for eligible Cloud branches. Any tenant with an active or pending desktop device receives a blocked preflight report for this release. A routed Cloud branch also refuses desktop pairing while its branch setting `ledger.order_payment_routing.v1` is enabled. Keep older payment events on their original routing contract. Cloud order completion v3 and customer return v2 carry the selected financial account and the GL identity used at posting.

Hybrid readiness requires the following work before the branch gate opens.

1. Define a cloud-authoritative, allowlisted branch payload. Preserve tenant, branch, chart, financial-account and terminal-to-bank UUIDs. Include eligible branch and business-wide rows. Carry only a dedicated checkout label, kind, currency, linked GL, eligibility and settlement destination. Represent verified physical terminal setup explicitly without copying merchant numbers, bank card numbers, IBANs or account holder details. Define how a locally created record conflicts with a Cloud UUID or GL binding.
2. Extend the pairing snapshot and ongoing Cloud-to-site refresh together. Apply branch and chart dependencies first, then bank/cash financial account rows, terminal rows and method bindings, followed by the branch routing revision. The canonical payment FK requires financial account rows to exist at the receiving peer. Archived mappings remain addressable for events already queued. A missing reference defers the exact event with a visible diagnostic until its mapping arrives. Keep settlement destination lookup independent of tender labels.
3. Require an acknowledged routing snapshot and event capability from every participating desktop. Inspect and drain or preserve each old-version queue before activation. A never-paired Full Offline installation needs the same checks and an explicit local authority policy for its chart and bank master before authoring versioned events. During compatibility rollout, use the old contract for old events, even if they arrive after activation.
4. Rehearse pairing, retry, lost acknowledgement, disconnected split tender, delayed delivery, archived source, return, settlement and rollback against isolated Cloud and site copies. Verify one posting per event, equal per-GL totals, consistent UUIDs, tenant and branch scoping, and absence of sensitive identifiers in the payload. Freeze new explicit routing through a versioned setting during rollback and preserve the source identity and journal of events already posted.
